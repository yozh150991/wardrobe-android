## 1. Швидкий старт для наступного агента

1. Прочитати `AGENTS.md`, цей документ і `README.md`. Визначити фактичну версію в `app/build.gradle.kts` та локальні зміни. Не брати старі розділи README за стан останнього релізу.
2. **Спільне приймання відкладено користувачем 10.10.2026** («Продовж. Тестувати будемо все разом»). Це не блокує погоджене продовження реалізації; автоматичні перевірки виконуємо. Коли починаємо тестування: REL-01 — актуальна Android-збірка, FAMILY-FOUNDATION-0.14.0.md → COLORS-0.13.10.md → CATEGORIES-0.13.9.md → PHOTO-PRECISION-0.13.8.md → PHOTO-QUALITY-0.13.7.md → PHOTO-INSPECTION-0.13.6.md → PHOTO-TOOLS-0.13.5.md → попередні PHOTO-01–04/R1/R2 і QA-01–02 на тому самому білді. До native-доказів статус verify. PHOTO-12–14 реалізовані (verify); PHOTO-11 та PHOTO-15–17 лишаються deferred; FAM-01 має реалізовану основу даних у 0.14.0, FAM-02 має реалізований обсяг у 0.14.6; FAM-03 shared editing/CAS і FAM-04 — наступний сімейний блок.
3. Використовувати наявні редактори, чернетки, фотообробку й операції збереження. Не створювати вдруге календар, статистику, капсули чи базовий екран сумісності покупки.
4. Перед зміною моделі даних перевірити міграції Room, backup, cloud snapshot, історію покупок і зв’язки образів. У базі зараз Room **10**, формат backup **10**. CustomCategory/CustomColor → Garment → purchase receipt/backup/cloud мають узгоджені посилання.
5. Для вибраного ID записати `in_progress`, виконавця та дату. Після роботи додати змінені файли, фактично виконані перевірки, обмеження та наступну конкретну дію в розділ 12.
6. Зберегти оновлений роадмап разом із кодом і включити його та `AGENTS.md` у наступний пакет/репозиторій. Якщо середовище має окремий файл роадмапу в ChatGPT, оновити той самий документ; не плодити суперечливі копії.

## 2. Мета продукту та незмінні домовленості

Wardrobe допомагає пам’ятати про наявний одяг і взуття, частіше носити забуті речі, складати образи та уникати непотрібних покупок. Орієнтир — понад 200 речей, кілька гардеробів, у тому числі сімейних.

| Домовленість | Наслідок для реалізації |
| --- | --- |
| Нативний Android, розповсюдження APK | Зберігати `applicationId=com.familywardrobe.app`. Оновлення на телефоні потребує того самого ключа підпису; не пропонувати видалення застосунку як звичайний крок. |
| Українська основна, також англійська та польська | Нові підписи, помилки, порожні стани й accessibility-описи мають бути в UA/EN/PL та ресурсах fallback. |
| Вхід email/пароль, відновлення посиланням | Немає кодів входу чи гостьового обходу авторизації. Чинна перевірена сесія може відкривати свої локальні дані офлайн. |
| Окремі акаунти членів сім’ї | Спільний логін на двох пристроях — поточна синхронізація одного власника. Це не виконання вимоги про сімейні ролі. |
| Свої речі, бажані товари й натхнення відрізняються | Не записувати бажання як куплене автоматично; режими підбору мають чесні мітки походження. |
| «Потреба» й «Знайдений товар» — різні стани | Зберігати початкові вимоги, бюджет, фото, посилання, історію переходів і безпечне скасування покупки. Бюджет і ціна — різні поля. |
| Фото можна обрізати, повернути, очистити фон і виправити розпізнавання | Постійно зберігаються кінцеві фото. Оригінали допустимі лише як тимчасові дані незавершеної обробки; потрібне коректне очищення. Фото завершеної історії покупки — окремий кінцевий референс. |
| Чернетки переживають перезапуск | Втрата мережі, скасування обробки й пізній результат не повинні стирати введене або змінювати іншу чернетку/акаунт. |
| Кілька палітр плюс незалежні System / Light / Dark | Нові екрани використовують поточну систему оформлення. Розмір шрифту до 200% і вузькі екрани — критерії приймання. |
| Хмара добровільна, локальні дані зберігаються | Без тихого перезаписування при конфліктах. Сімейний доступ має бути явним для конкретного гардероба. |
| Бажано мінімум витрат | Не обіцяти безкоштовність Firebase Storage. Перед платними сервісами/ML оцінити фактичну потребу й витрати; платні інтеграції не є затвердженою частиною цього плану. |
| Платежі й оформлення замовлення прибрані з продукту | Імпорт товару — збереження інформації. Оплата, доставка, власний маркетплейс не входять у найближчі релізи. |

## 4. Статуси й порядок випусків

`planned` — погоджений напрям, реалізація не почата; `partial` — базова реалізація вже є, потрібне розширення; `in_progress` — є виконавець і контрольна точка; `verify` — потрібні конкретні перевірки/підтвердження; `blocked` — записана фактична перешкода; `done` — критерії виконані й є докази; `deferred` — ідею збережено, але не включено в погоджений найближчий обсяг.

P0 — дані, доступ, збірка та блокери випуску. P1 — погоджений найближчий продуктовий обсяг або первинна незакрита вимога. P2 — наступні погоджені покращення. P3 — дослідження на пізніше. Не надавати дат завершення без оцінки й перевірки середовища. Номери майбутніх версій ще не призначені.

| Етап | Обсяг | Умова завершення |
| --- | --- | --- |
| R0. Приймання бази | `REL-01`, `QA-01–03`, `CLOUD-01`, `WIN-01`, `DOC-01` | Докази збірки й виконаних сценаріїв; усі невиконані кроки явно позначені. P0-дефекти виправлені до випуску. |
| R1. Найближче оновлення | `UX-01–02`, `IMP-01–03`; підготовка рішення `FAM-01` | Менше постійних елементів каталогу; товар із Share проходить перевірку й зберігається рівно один раз. |
| R2. Перед покупкою | `SHOP-01–03` | Пояснювані схожі речі й корисні нові поєднання на основі наявного гардероба. |
| R3. Сімейні гардероби | `FAM-02–04`, після `FAM-01` | Окремі акаунти, вибір гардероба, запрошення, перегляд/редагування, відкликання; серверні тести доступу. |
| R4. Особисті вподобання | `PERS-01–02` | Причини відмов впливають на наступні пропозиції; вподобання можна переглянути й скинути. |
| R5. Щоденне використання | `WID-01`, `ROT-01–02` | Віджет сьогоднішнього образу та керовані підказки для забутих речей. |
| R6. Подорожі | `TRIP-01–03` | Місто, дати, заняття, покриття днів і компактний набір із поясненням прогалин. |

R0 — перевірки, які супроводжують розробку, а не привід відкладати всі локальні зміни до отримання доступу до чужого телефона. Проєктування FAM-01 почати рано: воно вплине на збереження нових полів, але UI сімейного доступу не вважати готовим до серверного захисту.

### Як запускати існуючі перевірки

Ці команди описують перевірений у пакеті спосіб запуску; їх наведення не означає, що вони виконані в цій сесії.

Windows, з кореня оригінального проєкту:

```powershell
Set-Location "D:\Data\Downloads\Wardrobe\wardrobe-android"
$env:JAVA_HOME = "C:\Program Files\Java\jdk-17"
.\build-apk.ps1 testDebugUnitTest lintDebug assembleDebug
# Потрібен підключений тестовий Android-пристрій або емулятор:
.\build-apk.ps1 connectedDebugAndroidTest
```

Linux/macOS у середовищі з JDK/Android SDK:

```bash
python3 tools/check_project.py
bash build-apk.sh testDebugUnitTest lintDebug assembleDebug
bash build-apk.sh connectedDebugAndroidTest
```

Запускати також релевантні host-набори `tools/check_*.py` для зміненої логіки. `tools/run_host_checks.py` містить 22 набори, бере повну версію з Gradle та записує результати в `release-evidence/host-runs/<version>-<UTC-time>.json`. Старі звіти не перезаписуються.

Firebase emulator-тести з папки `cloud`:

```powershell
Set-Location .\cloud
npm ci
npm test
```

`cloud/package.json` фіксує Node 20/22 та локальний `firebase-tools`. Для входу/публікації використовувати CLI із цієї папки після встановлення залежностей; помилка `npx firebase login` у корені виникала через відсутність потрібного executable. Project ID береться з `app/google-services.json` → `project_info.project_id`. Тести працюють з `demo-wardrobe`, не з production.

На ПК користувача **Jenkins займає 8080**. У попередній розмові для Firestore Emulator погоджено **8088**; у базовому архіві `cloud/firebase.json` досі 8080. Перевірити локальне значення й вільність порту; зберігати налаштування користувача, не зупиняти Jenkins. Не вважати запропоновану зміну доказом, що її вже застосовано.

### Загальний критерій завершення функції

1. Основний шлях, порожній стан, валідація, loading, помилка/retry, cancel/Back, успіх і повторна дія мають визначену поведінку.
2. Вхідні дані й фото не губляться; перезапуск, зміна акаунта та конкурентна/пізня відповідь не порушують власність.
3. За зміни постійної моделі оновлені міграції, backup/cloud, історія та потрібні tests. Права перевіряються сервером, не лише UI.
4. Для нової поведінки є змістовні перевірки ризикових сценаріїв, а також фактична збірка й UI-приймання. Не додавати тести, які лише повторюють структуру коду.
5. Зберігаються UA/EN/PL, теми, TalkBack, вузький екран і великий шрифт; погоджений дизайн прийнятий у нативному застосунку.
6. У звіті окремо перелічені виконані й невиконані перевірки; task-ID, версія та докази оновлені. Якщо є невиконані обов’язкові кроки, статус `verify`/`blocked`, а не `done`.
7. Пакет містить поточні джерела, roadmap/AGENTS, інструкції оновлення й результати саме цього релізу. APK видається лише якщо він реально зібраний; конфігурація Firebase включається під час збірки, повторне підписання її не змінює.
