# Авторизація — 0.7.0

У 0.7.0 перевірена Firebase-сесія відновлюється при новому запуску. Перед відкриттям приватних даних перевіряється її власник і чинність. Явний вихід очищає SDK-сесію; відома недійсна сесія потребує повторного входу. Без мережі дозволено відкрити локальні дані раніше підтвердженого акаунта відповідно до правил FirebaseAuthBackend. Це зміна вихідного коду: реальні запуск, вихід, відкликання токена й офлайн-відновлення ще потребують Android-перевірки.

## Підключення

1. У цьому пакеті `app/google-services.json` уже додано з наданого файла. Проєкт: `wardrobe-75fea`, package name: `com.familywardrobe.app`. Файл клієнта залишається в `.gitignore`; він увійшов до цього приватного ZIP-пакета на запит користувача.
2. Email/Password уже ввімкнений згідно з наданим скриншотом Firebase Console. Використовується пароль; лист із посиланням потрібен для його відновлення.
3. У Authentication → Settings → Password policy встанови мінімум **12**, максимум **4096** символів, режим Require для нових паролів. Інтерфейс дозволяє пробіли й не нав’язує окремі вимоги до цифр/регістру. Увімкни email enumeration protection. Існуючі паролі на вході не перевіряються за новим мінімумом.
4. Перевір назву застосунку, відправника та шаблон Password reset у Templates. Використовується стандартна HTTPS-сторінка Firebase для зміни пароля. Код не треба вводити в додатку; після зміни пароля користувач повертається до входу. Протермінований/використаний лінк обробляє сторінка Firebase. Custom deep links і Firebase Dynamic Links не використовуються.
5. Не міняй Firebase project або applicationId між збірками для наявних користувачів: локальний простір прив’язаний до пари **project ID + UID**. Видалений і заново створений акаунт із тим самим email отримає інший UID і не успадкує старі локальні дані.
6. Виконай `python tools/check_auth_config.py`. Це перевірить форму клієнтської конфігурації та package name, але не стан серверних налаштувань.
7. Збери проєкт в Android Studio / через `build-apk.ps1` або `build-apk.sh` із JDK 17, Android SDK 35 та доступом до Google/Maven/Gradle. Запусти `testDebugUnitTest lintDebug assembleDebug`, потім `connectedDebugAndroidTest` на окремому тестовому пристрої. Для збереження даних установлюй поверх попереднього застосунку з тим самим applicationId і ключем підпису.

Офіційні джерела, перевірені 30.09.2026: [Android setup](https://firebase.google.com/docs/android/setup), [Email/password](https://firebase.google.com/docs/auth/android/password-auth), [Password reset](https://firebase.google.com/docs/auth/android/manage-users#send_a_password_reset_email), [Compose autofill](https://developer.android.com/develop/ui/compose/text/autofill). У 0.4.1 використано Firebase BoM 33.16.0 / Auth 23.2.1 і Google services plugin 4.5.0. Перевірено метадані офіційного Auth AAR: Kotlin 2.1.0, сумісні з Kotlin 2.1.20 у проєкті. Перевірку метаданих компілятора не вимкнено. Історичний результат повної збірки 0.4.1 — у docs/history/BASE-VALIDATION-0.4.1.md; він не підтверджує збірку 0.7.0.

## Поведінка

- Чиста установка й запуск після явного виходу починаються з Login. Збережена SDK-ідентичність спочатку перевіряється й лише потім відкриває власне локальне сховище. Повернення до вже відкритого застосунку та зміна орієнтації зберігають сеанс і поточний екран.
- Реєстрація, вхід, відновлення, видимість пароля, автозаповнення, польові помилки з фокусом, завантаження, мережева помилка, обмеження спроб і вихід реалізовані в Compose. Палітри та UA/EN/PL успадковані з 0.3.0. Пароль не обрізається й не записується в preferences, SavedState або логи; він існує в пам’яті форми/запиту SDK, очищається при завершенні/скасуванні або переході. Після повороту на екрані входу пароль треба ввести/автозаповнити знову.
- Скасування є логічним: пізня відповідь не відкриє гардероб. SDK-запит не можна примусово перервати, тому нове надсилання чекає його завершення. Уже створений акаунт або надісланий лист скасування не відкочує. Подвійний submit заблоковано.
- Відповідь відновлення однакова для відомого та невідомого email. Помилка входу не уточнює, чи існує акаунт. Серверні повідомлення/винятки не відображаються й не логуються як текст.
- При поверненні застосунку на передній план запитується свіжий токен. Відкликаний/недійсний сеанс закриває приватний UI повторним входом. Поточна форма, навігація та завершений результат обробки фото зберігаються для того самого UID; інший акаунт потребує явного виходу зі скасуванням чернетки. Відсутність мережі не завершує вже відкритий локальний сеанс. Новий вхід потребує мережі. Миттєве відкликання доступу на офлайн-пристрої не обіцяється.
- Вихід очищає SDK-сеанс, стек приватних екранів, ViewModel і тимчасовий кеш акаунта; збережені речі, фінальні фото та тема залишаються. Повторне відкриття того самого акаунта чекає завершення попереднього очищення. Видалення тимчасових файлів залежить від доступності локального сховища.

## Локальні дані та оновлення

Після першого підтвердженого входу, якщо є гардероб 0.3.0, користувач бачить email і явне підтвердження прив’язки. Атомарний реєстр власника записується **до** відкриття даних. Оригінальні `wardrobe.db`, фото та налаштування гардероба залишаються на місці — копіювання чи руйнівної міграції немає. Доступ до них матиме лише UID, якому їх прив’язали.

Інші акаунти отримують окремі Room DB, каталоги фото, тимчасові файли та preferences. ZIP-резервна копія охоплює дані лише відкритого акаунта. Тема та мова належать пристрою. FileProvider відкриває тільки `cache/camera`, а не корінь приватних даних.

Якщо обрати порожній гардероб, старий лишається без власника й може бути прив’язаний до іншого нового акаунта. Об’єднання вже створеного окремого акаунта зі старим сховищем автоматично не виконується. Пошкоджений реєстр зупиняє доступ і не призначає нового власника мовчки; не видаляй його для «виправлення». До переходу з 0.3.0 можна зробити звичайну ZIP-копію в самому додатку.

Хмарної синхронізації речей/фото в цьому пакеті немає. Той самий акаунт на іншому телефоні матиме окреме локальне сховище; перенесення виконується через ZIP. Спільні сімейні права, Google-вхід, зміна email і видалення акаунта не входять до цього етапу.

## Перевірка на пристрої — ще не виконана

| Сценарій | Очікуваний результат |
| --- | --- |
| Чиста установка / старт після виходу | Login без приватних даних; вибрана тема вже застосована |
| Холодний старт із раніше підтвердженою сесією | Перевірка, потім власний гардероб; повторне введення пароля не потрібне |
| Холодний старт із відкликаною сесією | Login; приватні дані не відкриваються |
| Холодний старт без мережі з підтвердженим SDK-акаунтом | Власний локальний гардероб і повідомлення про мережу; новий вхід потребує мережі |
| Порожні/помилкові поля, різні паролі | Точні повідомлення; фокус на першому помилковому полі |
| Створення акаунта / правильний пароль | Реальна відповідь Firebase, потім гардероб |
| Неправильний пароль / невідомий email | Однакова помилка входу, email збережено |
| Відомий / невідомий email для reset | Однакова відповідь; реальний лист тільки для відповідного акаунта |
| Reset link: чинний, використаний, протермінований | Hosted reset відпрацьовує; новий пароль входить, старий більше не входить |
| Немає мережі / забагато спроб | Відповідна помилка, повтор доступний без вигаданого таймера |
| Подвійне натискання / скасування під час повільної відповіді | Один запит; пізній успіх не відкриває даних; наступна спроба після завершення |
| Поворот під час входу / повторне створення Activity | Запит не дублюється; пароль не відновлюється зі SavedState |
| Старий гардероб: підтвердження / порожній варіант / скасування | Дані не втрачаються й не показуються не тому UID |
| Акаунт A → вихід → B → вихід → A | B не бачить речей/фото/резервної копії A; A знову бачить свої речі |
| Швидкий повторний вхід в A | Очищення старого кешу не видаляє нові тимчасові файли |
| Reset пароля або disable user під час відкритого редактора | Після перевірки сеансу — повторний вхід; той самий UID відновлює форму й готове фото |
| Нативна камера/галерея, reauth під час повернення | Фото залишається в правильному акаунті; дозволи й результат не переходять до іншого |
| Вихід → системний Back | Приватний екран не повертається |
| TalkBack, 200% шрифт, усі 3 мови й темна тема | Поля, помилки, прогрес і кнопки доступні без горизонтального обрізання |

Автоматичні інструментальні тести AccountStorageTest покривають прив’язку, збереження старого сховища, відмову іншому власнику, пошкоджений реєстр, ізоляцію фото/preferences та повторне відкриття окремих БД. Вони включені, але ще не запускалися на Android.
