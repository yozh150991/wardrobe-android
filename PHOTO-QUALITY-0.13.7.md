# Роздільність і переобробка фото — 0.13.7

11 жовтня 2026, Codex. PHOTO-09–10: реалізовано у вихідному коді, **verify**.
Android 0.13.7-release/code 26; Room/backup 8. Нового APK немає.
За вказівкою користувача Android-збірка та приймання виконуються спільним етапом.

## Як користуватися

У каталозі ввімкніть вибір речей → позначте потрібні → групові дії →
«Переобробити фото». Одна черга містить до 500 вибраних речей одного гардероба.
Якщо черга вже є, кнопка відкриє її без заміни незавершеної роботи.

Обробляється одне фото, після чого черга чекає рішення. Можна перемикати
збережене фото й новий результат, відкривати зум і бачити розміри/обсяг файла.
«Зберегти результат і перейти далі» замінює лише фото поточної речі та готує
наступне. «Залишити старе фото й пропустити» відкидає кандидат. Доступні
звичайна та сильніша обробка; кожен повтор починається зі збереженого фото,
а не з попереднього кандидата. Після невдалого аналізу показано причину.
Категорія, колір, назва, fingerprint та інші поля не змінюються цією операцією.

Повернення до каталогу залишає чергу доступною через «Продовжити переобробку
фото». Перезапуск зберігає перегляд, але не запускає ML автоматично.
Зупинка відкидає пізню відповідь; поточне завдання SDK може ще завершуватися.
Скасування решти черги видаляє непідтверджені результати, вже підтверджені
заміни залишаються. За відсутності предмета або зміни його фото заміна
блокується: пропустіть запис і виберіть актуальну річ знову.

Переобробка використовує наявне кінцеве фото. Видалені раніше деталі та
оригінал до старого ML не відновлюються. Для ручного виправлення залиште
старе фото й відкрийте звичайний редактор речі.

## Роздільність і пам’ять

| Максимальна heap-пам’ять застосунку | Межа очищеного PNG | Межа довгої сторони джерела | Межа декодованих пікселів |
| --- | --- | --- | --- |
| Менше 192 MiB | 1024 | 1800 | 3 240 000 |
| 192–255 MiB | 1536 | 1800 | 3 240 000 |
| Від 256 MiB | 2048 | 2560 | 4 194 304 |

Це консервативні програмні межі, а не вимірювання вільної пам’яті або гарантія
відсутності OOM. Фінальне квадратне полотно враховує фактичні непрозорі межі
предмета й 8% відступ. Масштабування предмета не перевищує 1:1; наприклад,
предмет 30 пкс отримує полотно 35 пкс із відступами. AI-superresolution немає.
JPEG тимчасового імпорту використовує quality 92 замість 85; модель та її
залежності не змінені. Старі/імпортовані великі фото перед ML також читаються
з обмеженим розміром. Картки мають окремий preview до 768 пкс, зум читає
збережений растр. Preview існує лише в пам’яті, додаткового файла немає.

Один ARGB-растр 2048² займає 16 MiB проти 4 MiB для 1024². Маски, історія,
ML і Compose потребують додаткової пам’яті. Розмір стисненого PNG залежить
від вмісту; попередня межа 25 MiB на фото залишається. Backup 8 і межа 20 GiB
розпакованих даних не змінені. Більші кінцеві фото збільшують час копіювання,
backup і обсяг добровільної хмарної синхронізації. Нових сервісів або
оплачуваного API не додано; заміри на цільовому телефоні ще потрібні.

## Збереження і захист даних

- Черга зберігається атомарно в каталозі конкретного акаунта. Вона не потрапляє
  в backup/cloud як кінцеві дані. Зміна Room або backup-схеми не потрібна.
- `Repository.writes` координує чергу, збереження, видалення та знімки backup.
  Джерела й кандидат захищені від очищення, поки є в незавершеній черзі.
- SQL замінює тільки `photoId` за збігом item ID, wardrobe ID і очікуваного
  source ID. Видалені записи не створюються заново, паралельні зміни полів
  не перезаписуються. Повтор кнопки/повтор помилки прив’язаний до конкретного
  кандидата та токена черги й не підтвердить наступний запис.
- Ім’я кандидата записується до створення PNG. Після перезапуску незавершений
  файл прибирається. Commit Room передує відпусканню старого фото; відновлення
  розпізнає вже завершений commit і просуває чергу рівно один раз.
- Список відпущених файлів зберігається до очищення. Файли, потрібні іншим
  речам/історії/чернеткам імпорту, не видаляються. Успіх видалення перевіряється.
- Cloud apply блокується на незавершеній або нечитабельній черзі, як і на інших
  локальних чернетках. Вихід із акаунта скасовує його scope і не відкриває
  чергу наступного акаунта.
- Нечитабельний файл черги не запускає обробку й не змінює збережені фото;
  екран пропонує скасувати чергу та вибрати фото заново. Невідомі файли при
  пошкодженому описі черги автоматично не вгадуються й не видаляються.

## Виконані перевірки

`docs/history/HOST-VALIDATION-0.13.7.json`: 18 наборів. Новий runner компілює й виконує
production Java правила: 108013 assertions для меж heap, odd dimensions,
power-of-two sampling, pixel cap, без збільшення та невідповідної маски.
Реальний PhotoCutoutRules обробляє synthetic 2048² під `-Xmx256m`;
фактичний час поточного запуску записано у host-звіті. Це не Android/ML benchmark.
14 перевірок виконують фактичний SQL заміни на SQLite: зміна лише фото,
stale/repeat, видалення, інший гардероб та окрема БД акаунта.

Підготовлено 9 Android-тестів `PhotoReprocessingTest` для справжніх
Room/AtomicFile/PNG із підміненою inference-функцією, 3 тести роздільності
`PhotoResolutionPersistenceTest`, оновлено очікування старого crop-тесту.
Ці Android-тести, Kotlin/Compose/KSP, Gradle/lint та APK **не виконувалися**.

## Спільне native-приймання

| Сценарій | Очікування |
| --- | --- |
| Нове фото камери, великі/непарні розміри, EXIF 1–8 | Пропорції й орієнтація правильні; межі декодування виконуються; очищений PNG до доступного ліміту |
| Маленька картинка, старий 1024 PNG, біла річ | Немає штучного збільшення; деталі не вигадуються; білий/кремовий фон і alpha збережені |
| 20–200 речей, картки, зум, ручний редактор | Заміряти peak heap, паузи, ML/PNG time; перевірити low-memory пристрій і landscape |
| Черга 1/2/200/500 фото, повторна кнопка | Зберігається тільки переглянутий кандидат; решта чекає; метадані та лічильники коректні |
| Model missing, timeout, пошкоджене фото, немає місця | Причина видима; поточна річ і старе фото збережені; повтор/пропуск/скасування доступні |
| Скасування в ML, PNG, під час черги | Пізній результат не повертає чергу; старе фото збережене; тимчасові файли прибираються |
| Kill до/після PNG, після Room commit, перед очищенням | Правильне відновлення перегляду/черги, без подвійної заміни й осиротілого кандидата |
| Інше ручне фото, зміна назви, видалення речі/гардероба | Змінене фото не перезаписано, метадані збережені, видалення не скасоване |
| Однакове фото в двох речах або історії | Очищення не видаляє спільне джерело; backup містить лише потрібні кінцеві фото |
| Sign out A → B → A, локальна черга і cloud apply | B не бачить файлів/черги A; A може продовжити; cloud apply чекає завершення локальної черги |
| Backup/export/restore на великому наборі | Виміряти розмір/час; чинні ID/формат 8, alpha, історія та дані зберігаються |
| UA/EN/PL, 200% шрифт, вузький екран, TalkBack | Кнопки й підписи доступні, екран прокручується; немає обрізання або стрибка фокуса |
