# FAM-03 — черги додавання речей і заміни фото, 0.14.17 / code 47

Статус: реалізовано, verify до CI цього PR і спільного native-приймання.
Гілка `feat/family-media-queue-0.14.17` залежить від PR #14.

## Поведінка

Додавання речей і заміни фото мають окремі FIFO-черги на спільний гардероб.
У кожній — до 10 чернеток і сумарно до 512 MiB готових архівів для надсилання.
Чинний ліміт одного архіву FamilyWire — 128 MiB; сумарна межа застосовується до кількох архівів.
Це ліміт активних publication ZIP; preview-фото, тимчасова побудова ZIP і старі orphan
каталоги потребують додаткового місця. Автоматичний GC залишається окремою задачею.

У додаванні можна зберегти чернетку, натиснути «Підготувати ще одну річ» та додати
наступну через камеру/галерею або копію власної речі. Кожна зберігається окремо.
Для заміни фото відкривається саме вибрана спільна річ; попередня чернетка іншої
речі більше не підміняє цей вибір. Одна заміна фото на річ. Список дозволяє вибрати
будь-яку чернетку для перегляду; видалення незапитаного або явно відхиленого запиту
зачіпає лише його архів і не змінює порядок решти.

Надіслати можна лише першу чернетку відповідної черги. Це послідовне явне надсилання,
не автоматичний batch і не фоновий sync. Додавання та фото мають незалежні черги;
між ними, metadata й outfits працює серверний CAS. Кожен ZIP є повним scoped snapshot:
після успішного надсилання першого наступний може мати стару baseRevision. Користувач
явно оновлює його перед надсиланням (або після підтвердженого конфлікту). Rebase
застосовує лише одну нову річ/фото до актуального snapshot, зберігаючи всі інші дані.
Для заміни фото це свідоме підтвердження нового фото поверх поточної версії.

Receipt-first retry залишає точні archiveId/baseRevision/hash/size після невідомого
результату. Навіть без локальних ZIP-байтів можна перевірити вже committed receipt.
Submitted без підтвердженого відхилення не можна відкинути або перебазувати.
Зміна вибору/покоління редактора блокує запізнілу камеру/галерею та queued prepare;
send/rebase/discard прив’язані до вибраної чернетки, тож подвійний клік не зачіпає наступну.

## Дані

- Ті самі account-private папки `family-additions` і `family-photo-replacements`.
- Per-remote journal v2 містить упорядкований список. v1 читається як один елемент;
  наступна успішна мутація атомарно записує v2 зі збереженням exact submitted payload.
- CAS перевіряє повну очікувану чернетку; ключ — garmentId усередині remote/kind.
  Rebase змінює publication archiveId, зберігаючи місце операції у списку.
- Пошкоджені/чужі/невідомі журнали, дублікати garment/archive, неправильні identity,
  перевищення кількості або bytes відхиляються без очищення чинних чернеток.
- Room/backup 10, signing/package/private wardrobe та live Firebase не змінені.
- Нові endpoints/rules/deployment не потрібні. Старий клієнт не підтримує journal v2;
  downgrade не підтримується, старий reader має відхилити v2 без очищення.

## Native-приймання разом

1. Підготувати 3 нові речі; перезапустити; відкрити кожну, перевірити поля/фото/порядок.
2. Підготувати фото для 3 різних речей; жодна форма не підміняється іншою чернеткою.
3. Надіслати head; явно оновити наступну та надіслати: попередня річ/фото збережена.
4. Видалити tail, rebase middle/head, втратити мережу/відповідь; решта журналу/архівів ціла.
5. Кілька rapid taps, пізня відповідь камери після переходу, зміна акаунта/ролі,
   revoke/lease/background; viewer не редагує, чужі фото не з’являються.
6. 10/11 чернеток, ліміт архівів/вільне місце, UA/EN/PL, 320 dp/200%, TalkBack.
