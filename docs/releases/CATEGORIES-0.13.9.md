# Wardrobe 0.13.9 — власні категорії та підкатегорії

CAT-01 / P1 / verify. 12 жовтня 2026, Codex. Code 28, Room/backup 9.
Реалізація в джерелах; APK не зібраний. Native-приймання відкладене користувачем на спільний етап.

## Як користуватися

1. У каталозі відкрийте «Категорії» → «Додати власну категорію», або зробіть це у формі додавання/редагування речі.
2. Введіть назву (1–60 символів), виберіть базовий тип одягу й збережіть. Наприклад, «Для бігу» → «Взуття».
3. Виберіть цю категорію для речі. Назва відображається на картці та в деталях; пошук знаходить її. Базовий тип залишається для підбору образів. Фільтр «Взуття» включає всі його власні категорії; фільтр «Для бігу» — тільки цю категорію.
4. Підкатегорія тепер одразу під категорією у формі. Введіть власну назву або виберіть наявну; вона зберігається разом із річчю. Окремий довідник порожніх підкатегорій не створюється.
5. У каталозі є видимий фільтр «Підкатегорія» з пошуком у списку. Він також є в розширених фільтрах. Список залежить від категорії й поточного гардероба, охоплює також архів/прання цього гардероба.
6. Загальний пошук охоплює назву речі, власну категорію, переклад стандартної категорії поточною мовою, підкатегорію, опис і місце. Частковий збіг, регістр, повторні/Unicode-пробіли та поширені варіанти апострофа нормалізуються. Кілька слів мають знайтися серед цих полів. Автоматичного перекладу введених користувачем назв немає.
7. Зміна категорії очищує залежний фільтр підкатегорії, інші фільтри лишаються. «Усе» у підкатегоріях скидає тільки її. «Скинути фільтри» очищує весь набір.

Власна категорія належить одному гардеробу, може існувати без речей, зберігається після виходу з форми. Дублікати назв власних категорій у межах гардероба нормалізуються. Редактор також попереджає про збіг із назвою стандартної категорії поточною мовою. Перейменування/видалення категорій не входило в цей запит.

## Дані й сумісність

- `custom_categories`: стабільний UUID, wardrobeId, name, normalized nameKey, baseCategory; унікальність назви в гардеробі. `Garment.customCategoryId` — nullable FK, базове `category` лишається стандартним.
- Room 8→9 додає таблицю, nullable поле й індекси, не переписує старі записи. SQL guards забороняють чужий гардероб/інший базовий тип для customCategoryId, FK захищає використану категорію.
- Чернетка й копіювання попередньої речі зберігають власну категорію. ML не перезаписує вручну вибрану власну категорію. Ручна зміна категорії очищує поле підкатегорії, після чого його можна заповнити заново.
- Backup 9 включає також порожні категорії. Restore створює нові UUID гардероба/категорій/речей, переносить посилання й purchase receipt; збережені образи лишаються прив’язані до речей. Backup 1–8 і старі receipts читаються з customCategoryId=null.
- Cloud використовує той самий формат 9, переносить категорії зі стабільними UUID; приймає існуючий snapshot 8. Зміна категорій робить дані dirty. Права власника не розширено.
- Нові резервні копії не призначені для старого застосунку. Не знижуйте версію БД на телефоні; встановлюйте новий APK поверх старого з тим самим ключем.

## Синхронізація: потрібне оновлення правил

Перед перевіркою cloud оновіть застосунок до 0.13.9 на обох пристроях і опублікуйте `cloud/firestore.rules` у власному Firebase-проєкті. Правила тепер дозволяють формати 8 і 9 та забороняють 9→8, щоб старий клієнт не стирав нові поля. До оновлення правил сервер із правилами 0.13.8 відхилить публікацію формату 9; локальне збереження категорій працює. Нові правила підготовлено в пакеті, у живий Firebase їх тут не розгортали.

Із папки `wardrobe-android/cloud`, використовуючи свій налаштований Firebase CLI:

```powershell
firebase deploy --only firestore:rules --project <YOUR_FIREBASE_PROJECT_ID>
```

Локальний firebase.json, client google-services.json, ключі, SDK та порти updater не змінює. Перед розгортанням виконати emulator-тести правил; DEV-01 не обходити.
