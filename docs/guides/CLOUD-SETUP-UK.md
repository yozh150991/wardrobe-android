# Хмарна синхронізація — 0.11.1

Клієнт Firestore + Storage, черга Room/WorkManager, інтерфейс статусу та вирішення конфліктів додані в проєкт. Сервіси й правила у вашому Firebase-проєкті ще не активовано в цій сесії. Реальна синхронізація потребує цих налаштувань і перевірки двох пристроїв.

## Підключення існуючого Firebase-проєкту

1. Збережіть свій `app/google-services.json`. У Firebase Console відкрийте саме проєкт, зазначений у його `project_info.project_id`. Застосунок залишається `com.familywardrobe.app`; не створюйте інший Firebase-проєкт для оновлення.
2. Authentication → Sign-in method: Email/Password увімкнений. Перевірте шаблон листа скидання пароля та його посилання. Вхід, реєстрація й скидання використовують існуючу Firebase Authentication.
3. Створіть Cloud Firestore у Native mode, базу `(default)`. Оберіть регіон перед створенням. Доступ відкривають тільки правила в `cloud/firestore.rules`, а не загальний test mode.
4. Створіть або відкрийте Cloud Storage. Для Storage потрібний тариф Blaze; вимога діє з 3 лютого 2026 року. Перевірте доступність bucket і його фактичну назву; нові bucket мають суфікс `.firebasestorage.app`, старі можуть мати `.appspot.com`. Це дані з [офіційного FAQ Firebase](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024).
5. Якщо конфігурацію Android завантажено до створення bucket, завантажте актуальний `google-services.json` для **того самого Android-застосунку**. У конфігурації має бути фактичний `storage_bucket`. Додатковий серверний ключ або service account у застосунок не потрібний.
6. Перевірте правила локально. У каталозі `wardrobe-android/cloud`, з Node 22 (або 20), Java для емуляторів і доступом до npm:

   ```bash
   npm ci
   npm test
   ```

   Тести працюють тільки з `demo-wardrobe` та локальними емуляторами. Вони перевіряють ізоляцію UID, допустимі версії, метадані, конкурентні транзакції, незмінність архівів і заборону видалення чинного архіву. У цій сесії всі 6 Auth/Firestore/Storage emulator тести виконані й пройшли, разом із 5 Android cloud SDK сценаріями. Production-проєкт не змінено.

7. Опублікуйте правила в існуючому проєкті. Спочатку перегляньте їх, особливо якщо цей Firebase-проєкт має інші застосунки: доданий deny-by-default потрібно узгодити з їхніми правилами. З каталогу `cloud`:

   ```bash
   npx firebase login
   npx firebase deploy --project YOUR_EXISTING_PROJECT_ID --only firestore:rules,storage
   ```

   Замість `YOUR_EXISTING_PROJECT_ID` використайте значення з наявного Android-конфігу. Під час публікації Storage rules погодьте запит Firebase на доступ правил Storage до Firestore. Це потрібно для захисту поточного архіву від видалення, як описано в [офіційній документації](https://firebase.google.com/docs/storage/security/rules-conditions#enhance_with_cloud_firestore).
8. Зберіть застосунок і встановіть його поверх старої версії з тим самим application ID та ключем підпису. Увімкніть «Хмарна синхронізація» в налаштуваннях на обох пристроях одного акаунта.

## Поведінка

Збережені гардероби, речі, кінцеві фото, потреби/товари, історія покупок і скасування, образи/колажі, носіння, календар, капсули та пакування синхронізуються як перевірений знімок акаунта. Ідентифікатори під час звичайного отримання з хмари зберігаються. Чернетки, незавершена черга фото, тема, мова, джерельні URI, дозволи на папки й тимчасові закріплення залишаються локальними.

Зміна даних і позначення черги виконуються в одній SQLite-транзакції. Зміни без інтернету та незавершене підтвердження завантаження переживають перезапуск. WorkManager чекає мережі й повторює тимчасові помилки з наростаючою затримкою. Застосунок також слухає оновлення серверної версії; фонове опитування приблизно раз на 15 хвилин залежить від обмежень Android. Точний час доставки не гарантується.

Публікація нової версії використовує Firestore-транзакцію з перевіркою попередньої версії. Зміни під час upload залишаються в черзі. Уже опублікований архів після втрати відповіді визнається підтвердженим; завантажений, але ще не опублікований архів повторно перевіряється й завершується. [Firestore-транзакції](https://firebase.google.com/docs/firestore/manage-data/transactions) потребують мережі; офлайн-черга належить Room, не Firestore.

Якщо обидва пристрої змінили дані від однієї базової версії, автоматичний перезапис зупиняється. Користувач бачить кількість гардеробів, речей і образів та обирає:

- версію цього пристрою — після підтвердження замінює хмарну;
- версію з хмари — спочатку зберігає локальний ZIP для відновлення, потім замінює дані;
- обидві версії — додає хмарні гардероби окремо з новими ID та збереженими внутрішніми зв’язками. Спільні речі можуть повторитися; це прямо пояснено до підтвердження.

Застарілий вибір відхиляється, якщо локальна чи хмарна версія змінилася. Незбережена чернетка або черга імпорту блокує заміну локальних даних. Вихід скасовує фонові завдання акаунта; операції перевіряють його UID перед застосуванням даних. Два екземпляри Room повідомляють один одному про зміни, щоб статус і колекція оновлювалися у відкритому інтерфейсі.

Архів обмежено 512 MiB, JSON — 8 MiB, фото — чинним лімітом PhotoStore. Знімок передається цілком, тому обсяг трафіку залежить від фото. Попередній архів видаляється тільки після успішного нового commit; чинний захищено rules. Після аварійного закриття можуть залишитися невикористані об’єкти: їх очищення в серверному сховищі має перевіряти, що об’єкт не є поточним `head.archive`. Не застосовуйте загальне age-based видалення до поточного архіву.

## Приймання на двох пристроях

Виконайте всі сценарії SYNC з `SCENARIO-COVERAGE-0.11.1.md`, включно з фотографіями, видаленнями, історією покупки, носінням і пакуванням. Окремо перевірте зміну акаунта під час upload/download, втрату відповіді після commit, три способи вирішення конфлікту, відновлення копії перед заміною та відмову через rules. До цих перевірок немає підтвердження, що синхронізація працює у вашому Firebase-проєкті.

## Підготовлений helper публікації

З папки `cloud`: `deploy-rules.ps1` показує read-only план з project ID/bucket вашого наявного конфігу. Після `npm ci` і `npx firebase login` команда `deploy-rules.ps1 -Deploy` перевіряє наявність CLI-акаунта, запускає 6 локальних тестів і публікує лише правила Firestore/Storage в цей самий проєкт. Helper не створює баз, не вмикає provider і не змінює billing. У цій сесії read-only план пройшов, а deployment правильно заблокований відсутністю адміністративного входу.

Native CloudEmulatorTest відтворюйте тільки на окремому порожньому AVD за `SCENARIO-COVERAGE-0.11.1.md`. Без `firebaseEmulatorHost=10.0.2.2` п’ять тестів будуть пропущені.
