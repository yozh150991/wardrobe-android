# Wardrobe — перевірка перед commit і push

Версія інструментів: **1.0.0**, 9 жовтня 2026. Це версія guard, не поточна версія Android. Поточна база — app/build.gradle.kts.

## Увімкнення на кожному комп’ютері

Потрібні Git і Python **3.9+** без сторонніх пакетів. На Windows — Git for Windows
(містить shell для hooks); Python можна встановити з https://www.python.org/downloads/.
Папка проєкту вже має бути Git-репозиторієм: використай наявний clone або виконай
`git init` у `wardrobe-android`, якщо репозиторію ще немає.

Mac / Linux / Git Bash, з папки проєкту:

```bash
sh install-git-safety.sh
python3 tools/git_safety.py check
```

Windows PowerShell:

```powershell
.\install-git-safety.ps1
py -3 tools/git_safety.py check
```

Якщо PowerShell не дозволяє запуск локального скрипта, еквівалентна команда:
`py -3 tools/git_safety.py install`. Глобальну політику PowerShell змінювати не потрібно.

Інсталятор зберігає активну копію перевірки всередині локального Git-каталогу
і налаштовує `core.hooksPath` **тільки для цього репозиторію**. Це зберігає захист
під час переходу на стару гілку, де файлів перевірки ще немає.
`.githooks/` — версійовані шаблони; `tools/git_safety.py` — джерело перевірки.
**Після clone на Mac/Windows та після оновлення guard повтори встановлення.**
Локальні Git-налаштування й активні hooks не переносяться звичайним push/pull.

## Що відбувається автоматично

- `.gitignore` виключає keystore, ключі, `.env`, service-account JSON за типовими
  іменами, `google-services.json`, локальні SDK/IDE-файли, build/cache,
  APK/AAB, архіви та бази. Публічний Gradle wrapper `.jar` лишається в Git.
- Особисті фото/експорти клади в `private/`, `personal-data/`, `user-data/` або
  `wardrobe-backups/`. Вони ігноруються. Звичайні ресурси зображень застосунку
  не блокуються лише через розширення; визначити особисте фото за вмістом guard не може.
- `pre-commit` читає **Git index**. Якщо в редакторі секрет уже прибрано, але
  staged-версія його містить, commit буде заблокований.
- `pre-push` читає всі refs із Git stdin і всі snapshot-файли вихідних комітів.
  Перший push/нова гілка перевіряє всю доступну історію. Видалений пізніше файл,
  перейменування, merge, тег на коміт і force-push не приховують старий секрет.
  База береться саме з refs одержувача, а не з усіх локальних remote-tracking refs.
- Пошук за вмістом знаходить приватні ключі, service-account JSON із довільним
  ім’ям, відомі формати токенів і підозрілі literal-паролі/токени. Значення не
  друкуються в звіті: лише шлях, тип проблеми та скорочений ID коміту.
- Якщо знайдено новий локальний credential-файл, до `.gitignore` додається
  **точний шлях**, без wildcard на сусідні файли. Власні правила зберігаються.
  Це працює і для нових неіндексованих файлів перед commit/push.
- Після зміни `.gitignore` дія зупиняється: переглянь і закоміть нові правила,
  потім повтори. Скрипт не додає нічого до index і не робить commit автоматично.
- Якщо секрет знайдено в `.kt`, `.java`, `.py`, документації чи іншому коді,
  файл **не ховається** через ignore. Потрібно виправити вміст.
- Файли не видаляються; індекс, історія, remote та підписи APK не переписуються.

`google-services.json` — клієнтська конфігурація, не приватний ключ Firebase Admin.
У цьому проєкті вона переноситься між комп’ютерами окремо.
Файли `.env.example`/`.sample`/`.template` дозволені за ім’ям, але перевіряються за вмістом.
Історичні журнали `release-evidence/*.log` дозволені за шляхом і також перевіряються.

## Якщо файл уже потрапив у Git

Додавання до `.gitignore` **не вилучає** файл із комітів.

1. Для локального файла, який потрібно зберегти на диску, прибери лише індексацію:
   `git rm --cached -- "шлях/до/файла"`.
2. Якщо секрет був лише в останньому **неопублікованому** коміті, після перевірки
   змін можна виправити його через `git commit --amend --no-edit`.
3. Якщо секрет є в давніших комітах, окремий commit із видаленням недостатній.
   Потрібно очистити відповідну неопубліковану історію. Guard цього не робить
   автоматично. Якщо секрет уже опубліковано, відклич/заміни відповідний токен
   чи пароль та окремо узгодь очищення історії; з signing key потрібен окремий
   план, щоб не втратити можливість оновлювати встановлений застосунок.

Перевірка всіх доступних refs і index: `python3 tools/git_safety.py audit`.
На Windows: `py -3 tools/git_safety.py audit`.
`check`/`audit` також можуть доповнювати `.gitignore`; секретних значень у звіті немає.

## Межі перевірки

Це локальний guard із визначеними правилами, а не гарантія пошуку всіх можливих
секретів. Невідомі формати токенів, персональні фото й довільні персональні дані
можуть не розпізнатися. Перевірка стосується файлів, не тексту commit/tag messages.
Блоби понад **10 MiB**, submodules, неповна shallow-історія та теги без коміту
блокуються, щоб не пропустити неперевірений вміст. Кеш результатів діє лише в межах
одного запуску. Зовнішніх мережевих запитів scanner не виконує.

Як і будь-який локальний Git hook, перевірка залежить від Git-клієнта та може бути
вимкнена користувачем. GUI-клієнт має підтримувати hooks; тест нижче запускає
справжній `git push` у локальний bare remote. Серверний захист GitHub є окремим шаром.

Дві відомі тестові конфігурації Firebase-емулятора дозволені тільки за **точним
шляхом + SHA-256 повного файла + конкретним правилом literal-warning** у
`tools/git_safety_allowlist.json`. Файли перевірено: вони обмежують host локальним
емулятором. Будь-яка зміна файла скасовує виняток; формат справжнього токена чи
приватного ключа не може бути дозволений цим списком. Нові винятки не додаються
автоматично. Після обґрунтованої зміни списку повтори інсталятор.

## Якщо інші Git hooks уже існують

Інсталятор відмовиться їх вимикати/перезаписувати. Залиши чинну систему hooks
і виклич `python3 <project>/tools/git_safety.py pre-commit` у своєму pre-commit.
Для pre-push передай його аргументи й **оригінальний stdin** у
`python3 <project>/tools/git_safety.py pre-push "$@"`; якщо кілька перевірок читають
stdin, збережи його й передай кожній окремо. Ненульовий exit має зупиняти дію.
Це окрема ручна інтеграція; стандартний інсталятор не вважає її виконаною.

## Перевірка інструментів

```bash
python3 tools/test_git_safety.py
```

Тести створюють тимчасові репозиторії, synthetic credentials і локальні bare remotes.
Реальні акаунти, GitHub і дані гардероба не використовуються.
Фактичні результати й обмеження платформи: `GIT-SAFETY-VALIDATION.json`.

Офіційні пояснення: https://git-scm.com/docs/githooks#_pre_push,
https://git-scm.com/docs/gitignore,
https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository.
